# 7. AI 와 일한 방식

이 프로젝트는 **Claude Code**(터미널에서 코드를 읽고, 고치고, 실행하는 AI 코딩 도구)와 함께 만들었습니다. 저장소 주인은 기획과 품질 판단을, AI 는 분석·구현·시험을 맡았습니다. 이 장은 그 방식과, 잘 된 점과 실패한 점을 솔직하게 적은 것입니다.

## 7.1 역할 나누기

| 사람 | AI |
|---|---|
| 원작을 기억하고 플레이하며 "이게 원작과 다르다", "이게 빠졌다"를 짚음 | 디컴파일 코드에서 해당 원작 함수를 찾아 읽음 |
| 무엇을 먼저 할지 정함 | Rust 로 옮기고 주석에 원작 함수 주소를 남김 |
| 공개 범위, 비밀번호, 배포 같은 결정 | 자동 진행 회귀 시험, 스크린샷·브라우저 시험 |
| 실제 폰에서 확인 | 커밋, 배포, 개발 노트(`AGENTS.md`) 갱신 |

사람이 한 일은 대부분 **짧은 한국어 문장**이었습니다. 예:
- "장수 출진 화면 원작과 너무 다른데?"
- "여포가 데미지가 안 들어가는데 원래 난이도인지 버그인지 체크만 해줘, 아무것도 수정하지 말고"
- "때리면 데미지가 얼마 들어갔는지 표기해주는 게 있었는데 빠졌어"

## 7.2 작업 고리

```
사람: 증상 하나 (원작과 다른 점)
AI:  원작 코드에서 원인 찾기 → 사람에게 원인 설명
     → (수정 요청이면) 옮기기 → 엔딩까지 자동 진행 시험 → 스크린샷 확인
     → 커밋 → 배포 → "무엇을 왜 고쳤고 무엇은 확인 못 했는지" 보고
사람: 실제 폰에서 확인, 다음 증상
```

5일 동안 이 고리를 수십 번 돌았습니다. 커밋 하나가 대개 고리 한 번입니다.

## 7.3 잘 된 점

- **"원작을 보고 그대로"라는 한 가지 기준.** AI 가 임의로 정한 값은 사람이 거의 반드시 알아챘습니다. 기준을 "원작 코드"로 정하자 논쟁이 사라지고 속도가 붙었습니다.
- **원인을 먼저 설명하게 한 것.** "체크만 해 줘"라는 요청에 AI 가 고치지 않고 원인만 보고하면, 사람이 판단해서 "원작 난이도로 바꿔 줘"라고 다음을 정했습니다.
- **회귀 시험을 배포의 문으로.** 엔딩까지 자동 진행이 통과해야 배포했습니다. AI 가 대담하게 고쳐도 게임이 깨지지 않았습니다.
- **개발 노트를 AI 의 기억으로.** 대화가 길어지면 AI 의 맥락이 요약됩니다. `AGENTS.md` 에 원작 함수 대응, 형식, 미구현 목록을 계속 적어 두어서, 요약 뒤에도 같은 수준으로 이어서 일할 수 있었습니다.
- **원작 리소스를 직접 읽는 작은 도구.** 대화상자·문자열 도구(`re/tools/`)를 만든 뒤로, 원작 화면을 "그럴듯하게" 만들지 않고 "그대로" 옮길 수 있었습니다.

## 7.4 실패한 점과 대책

| 실패 | 무슨 일이 있었나 | 대책 |
|---|---|---|
| **지어낸 값** | 연출 길이, 화면 배치를 원작 확인 없이 정함 → 사람이 "원작과 다르다" | 값마다 원작 함수 근거를 주석에 적게 함 |
| **옮기지 않은 함수가 조용히 빠짐** | 데미지 숫자, 퇴각 대사, 도구 연출, 행동 끝 표시가 없었음. 사람: "왜 자꾸 이런 식으로 빠지는지" | 원작 함수 목록과 구현을 대조하는 점검이 필요함 (재구현 방식의 구조적 약점) |
| **잘못된 판단으로 기능을 끔** | HP 창을 넣으면서 데미지 숫자가 필요 없다고 판단해 꺼 버림 | "원작에 있으면 둔다"를 기준으로 |
| **임의로 바꾼 설정** | AI 가 사이트 비밀번호 관련 설정을 사람과 상의 없이 바꿔 지적받음 | 비밀번호·공개 범위 같은 결정은 반드시 사람에게 물음 |
| **과장된 숫자** | 여포 데미지를 "거의 절반"이라 말했는데, 지형·장비를 뺀 어림값이었음. 사람이 바로 깨서 들통남 | 숫자에는 가정을 붙이고, 확신 정도를 구분해서 말함 |
| **검증 못 한 것을 된 것처럼** | 실제 아이폰에서만 나는 문제는 시험 브라우저로 재현이 안 됨 | "확인한 것 / 확인 못 한 것"을 나눠 보고 |
| **언어** | 작업 중 갑자기 영어로 답함. 사람: "왜 갑자기 영어질?" | 응답 언어를 노트에 명시 |

## 7.5 다른 사람에게 권하는 점

1. **기준을 하나로.** 재구현이면 "원작 코드", 리메이크면 "디자인 문서". 기준이 있어야 AI 의 산출물을 빠르게 판정할 수 있습니다.
2. **처음부터 자동 진행 시험을 만드세요.** AI 와 일하면 변경이 빠르고 많습니다. 사람이 매번 끝까지 플레이할 수는 없습니다.
3. **"고치지 말고 원인만"을 자주 쓰세요.** 판단은 사람이, 실행은 AI 가 하게 됩니다.
4. **노트 파일을 AI 와 같이 키우세요.** 긴 작업에서 AI 의 기억을 대신합니다.
5. **되돌리기 어려운 일은 사람이 정합니다.** 공개, 비밀번호, 기록 다시 쓰기, 배포 대상 같은 일입니다.
